# 仓库架构与推进方式

## 组织方式

采用一个案例库仓库，以 **SaaS / PaaS / IaaS → 领域 → 案例** 为主结构。统一首页先选择服务模型，再按其下属领域发现案例。每个案例拥有自己的规格、数据、运行入口和证据，可以独立演进。

`catalog/service-models.json` 定义三个一级服务模型，`catalog/domains.json` 定义服务模型下的领域，`catalog/cases.json` 索引实际案例。版本 2 的 `case.json` 声明 `serviceModel` 和 `domain`；路径固定为 `examples/<serviceModel>/<domain>/<case>/`。领域只有一个父服务模型，案例 ID 全仓库唯一，标签负责跨领域发现。

服务模型标记案例面向的目标能力，不承诺代码模板已被托管为云服务。分类、交付状态和部署方式是独立维度：同一个 SaaS / MES 工作台可以本地运行、企业自托管或使用公共云后端，仍按业务应用分类。具体定义和分类边界见 [领域分类](domains.md)。

统一目录服务不需要登录或数据库。目录下的案例按自己的集成声明运行：离线原型可以使用合成数据；连接真实服务的工作台需要所选身份、业务和资产服务。首页显示字典中的全部类别，实际案例数量只来自案例索引，不用空目录表示已交付能力。

## 与上游组合

设计系统负责稳定的视觉和交互组件；digital-employee 负责需要 Agent 的执行契约；文档和记忆能力按案例引用；本仓库负责业务语义、工作台与可复现的案例证据。接入记录放在案例 `integrations.md`，代码中只引入实际使用的依赖。

完整工作台以 `examples/<serviceModel>/<domain>/<case>/workbench/` npm workspace 纳入根锁文件。`npm run build` 构建各工作台，`npm run demo` 构建后在 <http://127.0.0.1:4173> 提供统一目录；`runtime.entry` 相对于案例目录指向实际构建入口。构建输出被忽略，检查从干净依赖安装开始，不依赖来源机器的二进制或依赖目录。

分类迁移必须同时修改 manifest、catalog、目录、npm workspace 模式、测试 fixture 路径和文档相对链接。`npm run check` 检查分类父子关系、案例路径、索引一致性及已声明能力的本地验证；它不代替真实服务联调。

## 运行与数据提供方

三个运行维度独立维护：

| 维度       | 回答的问题                                   | 存放位置                                         |
| ---------- | -------------------------------------------- | ------------------------------------------------ |
| 分类       | 这个工作台服务于哪一层、哪个领域？           | `serviceModel`、`domain`、tags、目录路径         |
| 交付证据   | 当前实现了什么，哪些服务真正连接？           | status、capabilities、`evidence/verification.md` |
| 部署与数据 | 在哪里运行，连接哪个身份、数据库和资产服务？ | `integrations.md`、本地配置、提供方实现          |

工厂运营工作台通过 `IdentityProvider`、`OperationsRepository` 和 `AssetStore` 接入身份、业务数据和资产。当前有 Supabase 组合及标准 HTTP 客户端；企业可按 [数据提供方契约](data-provider-contract.md) 实现 MySQL 与既有资产平台后端。端口可以组合，跨服务的身份与授权须由实际实现统一处理。

工厂工作台以工厂申领和现场执行为主要对象，因此归 `saas/mes`；CRM 标签关联销售拜访。Supabase 作为后端选择不改变案例分类。若将来收录面向开发者管理后端项目、身份配置和数据接口的平台工作台，再根据目标能力考虑 `paas/baas`。

Persona Studio 归 `saas/dam`，使用 localStorage 保存本浏览器演示状态，刷新保留；简版 demo/ 保留内存重置流程。该案例没有真实多用户共享、媒体上传或生成模型接入。

## 从客户需求到案例

1. 需求访谈：了解目标、当前流程、输入输出与成功标准；保留内部获准来源。
2. 规格抽象：把具体客户需求提炼成可复用案例，区分事实、提议与待确认项。
3. 原型验证：先用合成数据跑通主流程，获得业务反馈。
4. 服务接入：连接素材存储、业务 SaaS 或模型，记录接口、配置与失败处理。
5. 验收与沉淀：在声明环境完成标准，更新状态、证据和案例目录。
