# 仓库架构与推进方式

## 分类和资产关系

统一目录按 **服务模型 → 业务族 → 领域** 查找业务，再按 **标准主干 → 场景变体 → 案例实现** 复用方案。分类回答“解决哪类问题”，资产关系回答“哪些部分可以复用”。

| 文件                          | 内容与关系                                                 |
| ----------------------------- | ---------------------------------------------------------- |
| `catalog/service-models.json` | SaaS、PaaS、IaaS 三种服务模型                              |
| `catalog/domain-groups.json`  | 业务族，属于一个服务模型                                   |
| `catalog/domains.json`        | 领域，属于一个服务模型及其业务族                           |
| `catalog/blueprints.json`     | 标准主干，属于一个领域，定义角色、对象、流程、页面和扩展点 |
| `catalog/variants.json`       | 场景变体，引用一个主干，记录适用行业和差异                 |
| `catalog/cases.json`          | 实现索引，关联主干、变体及唯一代码目录                     |

主干和变体是参考设计，允许暂时没有实现。案例目录必须有真实材料，禁止用空目录或重复实现充数量。当前有 60 个 SaaS 分类、22 个主干、44 个变体、两个参考实现；项目案例为零。

版本 3 的 `case.json` 与索引声明 `serviceModel`、`domain`、`blueprintId`、`variantId` 和 `caseKind`。案例所属领域必须与主干一致，变体必须属于该主干。目录仍为 `examples/<serviceModel>/<domain>/<case>/`，不会把代码复制到每个场景分支。跨领域发现用 tags。

## 目录浏览与实现运行

目录服务是本地静态应用，读取已校验的 JSON，提供业务族、领域、行业、关键词和资产类型筛选。选择主干或变体可以查看规格及关联实现，URL 保存浏览位置。所有目录材料无需登录或数据库。

`npm run demo` 构建案例后在 <http://127.0.0.1:4173> 提供统一入口。案例的 `runtime.entry` 相对于其目录指向实际构建产物；完整工作台以 `examples/*/*/*/workbench` npm workspace 纳入根锁文件。构建输出不提交。

案例按自己的集成声明运行。Persona Studio 是本浏览器合成数据演示，使用 localStorage 保留演示状态；工厂工作台已实现独立身份、业务和资产提供方。目录新增分类、主干或变体不需要新建账号、数据库表或云租户。

## 独立维护的维度

| 维度         | 回答的问题                               | 位置                                             |
| ------------ | ---------------------------------------- | ------------------------------------------------ |
| 分类         | 面向哪一层、哪种业务？                   | serviceModel、groupId、domain、tags              |
| 标准化复用   | 沿用什么主干，改变哪些业务规则？         | blueprintId、variantId、主干和变体字典           |
| 来源与成熟度 | 是参考实现还是项目案例，已验证到哪一步？ | caseKind、source、status、capabilities、evidence |
| 部署与数据   | 在哪里运行，连接哪些服务？               | integrations.md、部署配置、提供方实现            |

SaaS 分类表示业务应用方向，不承诺提供托管云服务。使用 Supabase 不改变工厂案例的 SaaS / MES 归属。数据库、资产平台和身份系统分别通过 [数据提供方契约](data-provider-contract.md) 接入；MySQL 或其他服务由部署者按契约实现，目录资产格式不绑定厂商。

## 沉淀与协作

1. 先检索已有主干、变体和案例，明确哪些能力已经实现。
2. 用获准来源抽象需求，选择现有主干，记录场景差异；没有合适主干时补充其标准内容。
3. 复用适用的实现，记录实际代码和外部依赖，保留模拟、不可用、已连接能力的区别。
4. 用合成数据验证主流程，按项目需要接入服务并留下检查记录。
5. 有可公开项目材料时，按规范收录项目案例；从多个项目中识别稳定共性，回收到主干，保留差异的变体关联。

是否拆成新变体取决于角色、流程、数据约束是否真正变化，不取决于换了客户名字、配色或数据库。参考设计本身不证明业务交付能力，项目案例也不自动达到 `verified`。

## 校验与上游

JSON Schema 校验字段结构，仓库校验器验证分类父子关系、主干和变体引用、索引与 manifest 一致性、文件路径和证据文件。单元测试覆盖无效引用和不一致关系，浏览器测试覆盖筛选、关联浏览、历史、错误恢复和手机布局。

`npm run check` 执行本地构建与结构、业务规则验证；`npm run test:e2e` 执行目录与案例浏览器回归。它们不能自动判断客户证据真实性、授权范围或验收结论，需要收录者审查。

设计系统提供稳定组件，digital-employee 提供 Agent 执行契约，其他仓库按案例引用。本仓库维护业务语义、复用关系、工作台实现与证据，只有实际使用的依赖才写入接入声明。
